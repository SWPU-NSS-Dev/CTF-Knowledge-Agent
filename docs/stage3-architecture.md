## Structured graph and evidence (storage)

New `KnowledgeStorageMixin`, Store inherits it, `_initialize_stage3()` called by Store initialization including restore. Separate versioned migration table, backup naturally includes all tables. Maintain FK integrity, indexes, short transactions.

Entity kinds: challenge, writeup, vulnerability, root_cause, attack, fix, exploit, patch, knowledge, tool, precondition, verification. Each: id,kind,title,description,attributes:dict,evidence:list,provenance ('source_claimed'|'ai_extracted'|'human_authored'),verification_status ('unverified'|'human_verified'|'rejected'),revision:int,created_at,updated_at. Attributes store competition/year/category/vulnerability_type or original article_id/version; explicit IDs and edges carry relationships. No human_verified on create/update. Editing a reviewed record resets to unverified and increments revision. Referenced source article/version evidence is immutable and exact.

Evidence schema: article_id,version,start,end,quote. Require valid stored article_version (not only current), integer range, exact quote=content[start:end], quote non-empty. Return enriched source_url/raw_path/title (join current article identity + referenced historical version) and source_status='source_claimed'. Optional evidence is allowed on human-authored entity, but human verification requires non-empty evidence and review note. Relationships always require non-empty exact evidence; are `candidate` until explicit manual review. Rejected records retained with audit. Revising an endpoint invalidates verified relation conclusions: relation serialization must expose endpoint revision changes and treat stale verification as candidate until reviewed again. No arbitrary SQL/Python from attributes.

Supported relationship kinds and endpoints: challenge_writeup(challenge->writeup), challenge_vulnerability(challenge->vulnerability), writeup_knowledge(writeup->knowledge), writeup_attack(writeup->attack), writeup_fix(writeup->fix), vulnerability_root_cause(vulnerability->root_cause), vulnerability_attack(vulnerability->attack), vulnerability_fix(vulnerability->fix), vulnerability_knowledge(vulnerability->knowledge), attack_precondition(attack->precondition), attack_exploit(attack->exploit), attack_fix(attack->fix), fix_patch(fix->patch), fix_verification(fix->verification), knowledge_tool(knowledge->tool). Validate endpoints/types, forbid self edges; duplicate semantic edge may return existing record only when identical evidence/content, otherwise update explicitly. Relation fields id,source_id,target_id,kind,rationale,evidence,provenance,status ('candidate'|'human_verified'|'rejected'),revision, endpoint revision snapshots, times.

Store methods (dict payload, ValueError for validation; missing IDs may return None on reads):

- create_entity(payload:dict)->dict; update_entity(id,payload:dict,*,expected_revision:int)->dict (raise dedicated RevisionConflict on stale writes); get_entity(id)->dict|None.
- list_entities(*,kind=None,q=None,limit=50,offset=0,filters:dict|None=None)->list[dict]. Whitelisted filters competition/year/category/vulnerability_type/verification_status/source; SQL filtering before pagination, not Python filter-after-LIMIT.
- create_relation(payload:dict)->dict; update_relation(id,payload,*,expected_revision)->dict; get_relation(id)->dict|None; list_relations(*,entity_id=None,kind=None,status=None,limit=50,offset=0)->list[dict]. `get_relation`/list include source/target entity summaries and evidence metadata.
- related(entity_id,*,depth:int|None=1,limit:int|None=50)->dict with entities,relations,warnings; visited detection; depth/limit explicit warnings on truncation; default excludes rejected edges but distinguishes candidate/verified.
- find_attack_fix(query:str='',*,entity_id:str|None=None,limit:int=20)->dict: query vulnerability/challenge/root cause/title, traverse explicit links in both directions to associated attacks/fixes/patches; return entities,relations,comparisons:list[dict],warnings. Each comparison identifies attack/fix/patch IDs, rationale, evidence and candidate versus verified status; missing links are absent not invented. A patch query must find corresponding attack through fix edges; challenge/writeup scopes supported.
- review_record(target_type:'entity'|'relation'|'knowledge',target_id,decision:'human_verified'|'rejected',*,note,reviewer,expected_revision)->dict. Require note/reviewer, evidence for verify, record before/after with target revision; request authenticated user action is manual review (never let model call this). For stage2 knowledge cards add revision compatibly, edits preserve extraction/original content audit and reset verification. `update_knowledge(id,payload,*,expected_revision)` supports title/content edits only; `list_reviews(...)->list`, `pending_reviews(limit=50,offset=0)->list` unified review queue. Do not allow payload to set verification state directly.
- knowledge_stats()->dict counts by entity kind/relation kind/status/review, chunks/vectors/model manifests useful for UI. Existing stats includes stage3_schema_version and graph counts without dropping prior keys.

Fixture: at least one challenge with 2 distinct writeups, a vulnerability/root cause, one attack/exploit and 2 fixes/patches with different tradeoffs plus verification steps. Store original Markdown fixture via normal ingest; all graph claims quote exact original evidence. Include conflicting/candidate association and review transition. Fixtures must not pretend a public contest live fetch. Supply reusable `ctfka.knowledge.fixtures.seed_awdp_fixture(store)` ONLY on explicit CLI/demo/test request, never silently on production startup; returns IDs for acceptance/UI exploration.

## Read-only multi-step Agent (agent/tools)

`AgentService(settings,store,provider)` exposes async `answer(question:str,*,entity_id:str|None=None,model:str|None=None)->dict`, and async `tool(name:str,arguments:dict)->dict` for allowlisted read-only tools. Names: search_knowledge,search_writeups,read_article,find_related,compare_solutions,find_attack_fix. Tool schemas validate args; article lookup only by stored ID/version, no filesystem paths or URLs. Unknown tools rejected. Source strings cannot request/dispatch tools. Deterministic plan based on query/category/entity IDs, not autonomous arbitrary model actions: search relevant entities/articles, read chosen original paragraphs, traverse graph, compare solutions; record explicit trace per tool (name,args,elapsed,status,result_count). At least 2 useful calls in nontrivial evidence-bearing queries, no repeated identical calls. Tool count enforced before invocation; cancellation/timeout closes model generation. Optional None limits permitted, repeated-call detection remains.

Return answer,model,citations,grounded,inference_status='ai_inferred',usage,tools_used,trace,relations,comparisons,warnings. Model receives fixed system policy, graph statuses and original quotes as separate untrusted data, final user question. Enforce context budget using both effective LLM context and Agent setting, reserve output, do not truncate code evidence. Valid citations need exact stored historical source/version/range and labels [S1]. Unknown cited labels -> grounded=false and warning. Candidate relations always marked, neither prose nor metadata presented as verified. If no local model, return explicitly labelled deterministic evidence/comparison report, inference_status='deterministic_evidence', still usable and truthful. No evidence -> explicit no-evidence. Existing RAG service should remain compatible; reuse its helpers where useful without changing its ownership.

New source module `sitemap`: sitemap XML/urlset and recursive sitemapindex discovery via existing FetchClient, defusedxml, dedupe/cycle detection, same-origin public-site defaults, optional include/exclude regex, configured sitemap_urls. No hard-coded item/depth cap; SourceConfig.max_items and cancellation apply. Fetch/parse/normalize/validate standard SourceAdapter. Registration only touches registry/builtin declaration, no core scheduler/API logic. Docs configuration for CTF Archives or other public sites can use generic adapters; no claim live website success without actual run.
